Mounting TorBox storage with rclone over T3 — the config that actually works

Your TorBox cloud, visible as a local drive, streaming your own library. The exact endpoint settings, the read-only reality, and the media-server patterns people run on it — tested, not theorized.

What T3 is

T3 is TorBox's S3-compatible read endpoint for your cloud storage (AirLock + your downloads). Any tool that speaks S3 — rclone, Mountain Duck, scripted aws-cli calls — can list and fetch your files. The practical use: mount your TorBox library as a filesystem and point media software at it.

The rclone config that works

[torbox]
type = s3
provider = Other
endpoint = https://t3.nexus:443
access_key_id = YOUR_AUTH_ID
secret_access_key = YOUR_API_KEY
region = us-east-1
force_path_style = true

The four lines people get wrong:

  • endpoint = https://t3.nexus:443 — not torbox.app, not api.torbox.app. The T3 host is its own thing.
  • Keys are swapped from what you'd guess: access key = your Auth ID (dashboard → settings), secret = your API key. Not two API keys.
  • force_path_style = true — virtual-hosted addressing (bucket.t3.nexus) doesn't resolve; path style does.
  • Signature: aws signature v4 (rclone default) works; no custom signer needed.

Sanity check: rclone lsd torbox: should list your storage buckets immediately.

The read-only reality

T3 is a read endpoint. You can list, download, and stream — you cannot upload, rename, or delete through it. New downloads still enter the cloud the normal way (web, API, RSS). Any workflow that "writes" to the mount needs a different design: organize by controlling what goes IN (see the music-server pattern below), not by moving files after.

Mounting

rclone mount torbox: /Volumes/torbox \
  --vfs-cache-mode full \
  --vfs-cache-max-size 20G \
  --read-only \
  --daemon
  • --vfs-cache-mode full is the important one for media: it caches file data locally as you stream, so seeks and scrubbing don't re-fetch ranges repeatedly. minimal works for plain sequential playback; full makes music servers and scrubbing usable.
  • --read-only — matches reality; prevents apps from trying writes that would silently fail.
  • Cache size is your disk decision; 20G handles a few concurrent FLAC streams comfortably.

Pattern: music server without local storage (Navidrome-style)

The thing everyone asks: "can I point a music server at TorBox and stream my FLACs?" Yes — with one design rule. Since the mount is read-only, the library must arrive already-organized:

  1. Organize at ingest, not after. Downloads land in whatever structure the torrent had. The trick people use: a small sync step that mirrors torbox:Music/ into a local (or nas) folder structure Artist/Album/track.flac as files download — or manage the cloud side via the API so music lands in a Music folder you keep curated.
  2. Point the server at the mount (or the synced mirror). Navidrome reads folder structure; it doesn't write, so read-only is fine.
  3. Let the server's own database live locally — only point its music folder at the cloud. Databases on a network mount get slow and weird.
  4. Upload tools (Lidarr-style) that want to move/rename files can't operate on the mount itself — they manage a local mirror, and the mirror is what the server reads. The cloud is the source that mirror syncs from.
The honest summary: T3 turns TorBox into a read-only NAS in the sky. Streaming, listing, syncing down: excellent. Using it as a writable drop target for library managers: not what it is. Design around read-only and it's genuinely great — a 1 TB cloud slice mountable on every machine you own.

Streaming a single file without mounting

Don't need a mount? rclone can serve too:

rclone serve http torbox: --addr 127.0.0.1:8080

gives you a local HTTP file browser over the cloud — handy for one-off playback or fetching a file into an app that only speaks URLs.
